# ТЗ: Веб-интерфейс PayBridge (для третьего участника)

**Кому:** третьему участнику команды, отвечающему за веб.
**Контекст:** кейс Space Payments «Генератор интеграций». Роли в команде: (1) тимлид —
ядро-генератор `Paybridge::*` + CLI; (2) напарник — проверка/качество/документация/демо
(`ТЗ_напарник.md`); (3) **ты — веб**. Основной интерфейс по решению команды — **CLI**;
веб — дополнительный слой поверх того же ядра (наглядная демонстрация и «доп. идея»).
Твоя зона — веб-сервис, который даёт ядру пользовательский вход/выход.

**Ограничения кейса (жёстко):** только Ruby, открытый исходный код, никаких проприетарных
сервисов, **никаких нейросетей**. Репозиторий публичный, дедлайн коммита 23:00. Нарушение → дисквалификация.

> База уже есть: рабочий скелет на Sinatra в `app/` (маршруты, стор, тесты `rack-test`,
> страница `public/index.html`). Твоя задача — довести его по бэклогу ниже.

---

## 1. Границы ответственности

| Ядро-генератор (не твоё) | Бэкенд (твоё) |
|--------------------------|----------------|
| Парсинг YAML → IR | Приём файла спецификации по HTTP |
| Маппинг статусов/ошибок/полей | Валидация входа (формат, размер) |
| Рендер `*_service.rb`, `INTEGRATION.md`, `fixtures.json` | Запуск генератора, сбор результата |
| Отчёт о предупреждениях (`report`) | Отдача файлов (inline / скачивание / zip) |
| — | История запусков, статусы, ошибки в понятном виде |

Ты **не** парсишь спецификацию сам. Ты вызываешь ядро через один фасад (ниже) и отдаёшь то, что оно вернуло.

## 2. Контракт с ядром — единственный шов между вами

Договоритесь об этом методе в первую очередь; дальше можно работать параллельно с заглушкой.

```ruby
# lib/paybridge.rb
module Paybridge
  # Единая точка входа. Бэкенд знает только её.
  # spec_path — путь к загруженному YAML.
  # provider  — имя провайдера (строка из запроса, напр. "novapay").
  # Возвращает Paybridge::Generation.
  def self.generate(spec_path:, provider:, config_path: DEFAULT_CONFIG)
    # ...
  end

  # Результат генерации.
  Generation = Struct.new(
    :provider,     # "novapay"
    :files,        # { "novapay_service.rb" => "<код>", "INTEGRATION.md" => "...", "fixtures.json" => "..." }
    :warnings,     # ["Статус 'x' не найден...", ...]  (report ядра)
    :endpoints,    # [{ method:, path:, role: }] — для превью в UI
    keyword_init: true
  )

  # Ошибка разбора/генерации — бэкенд ловит её и отдаёт 422.
  class GenerationError < StandardError; end
end
```

**Заглушка на старте** (пока ядро не готово): верни фиктивный `Generation` с тремя файлами-строками. Так фронт и API проверяются независимо.

## 3. Стек

- **Ruby 3.2+**, веб — **Sinatra** (+ `rackup`/`puma`). Всё open source. Rails допустим, но избыточен для хакатона.
- Хранилище: файлы результата — во временной папке `storage/<id>/`; метаданные — **SQLite** (`sqlite3` gem) либо, для простоты, in-memory + JSON на диск. Выбери одно, не усложняй.
- Архивация: `rubyzip` (open source) для `GET /archive`.
- Тесты: **minitest** (stdlib) + `rack-test`.
- Фронт (если делаете): статическая страница из `public/` — форма загрузки + вывод результата. Отдельный SPA не нужен.

## 4. HTTP API

Базовый префикс `/api`. Формат ответов — JSON (кроме скачивания файлов).

| Метод | Путь | Назначение |
|-------|------|-----------|
| POST | `/api/integrations` | Загрузить спецификацию, сгенерировать интеграцию |
| GET | `/api/integrations/:id` | Метаданные + список файлов + предупреждения |
| GET | `/api/integrations/:id/files/:name` | Содержимое одного файла (text/plain) |
| GET | `/api/integrations/:id/archive` | Zip со всеми файлами |
| GET | `/api/health` | Проверка живости |

### 4.1 POST /api/integrations

**Запрос:** `multipart/form-data`
- `spec` — файл `provider_api.yaml` (обязателен)
- `provider` — строка, напр. `novapay` (обязателен, `^[a-z][a-z0-9_]{1,32}$`)

**Успех — `201 Created`:**
```json
{
  "id": "int_7f3a9b2c",
  "provider": "novapay",
  "status": "generated",
  "endpoints": [
    { "method": "POST", "path": "/payouts", "role": "create" },
    { "method": "GET",  "path": "/payouts/{payout_id}", "role": "status" }
  ],
  "files": ["novapay_service.rb", "INTEGRATION.md", "fixtures.json"],
  "warnings": [],
  "created_at": "2026-09-03T16:40:00Z"
}
```

**Ошибка валидации входа — `400`:** отсутствует файл / битый `provider`.
**Ошибка разбора спеки (`GenerationError`) — `422`:**
```json
{ "error": { "code": "generation_failed", "message": "Некорректный YAML: ..." } }
```

### 4.2 GET /api/integrations/:id/files/:name

Отдаёт содержимое файла с `Content-Type: text/plain; charset=utf-8` и
`Content-Disposition: attachment; filename="<name>"`. Неизвестный `id`/`name` → `404`.

### 4.3 GET /api/integrations/:id/archive

`application/zip`, имя `integration_<provider>.zip`, внутри — все файлы плюс копия `base_service.rb`.

## 5. Модель данных

```
Integration
  id           string   (int_<hex>)
  provider     string
  status       string   (generated | failed)
  warnings     json (array<string>)
  files        json (array<string>)   # имена; содержимое лежит в storage/<id>/
  error        string?                # текст, если failed
  created_at   datetime
```

Файлы результата пишутся в `storage/<id>/`. `id` генерируй как `"int_" + SecureRandom.hex(4)`.

---

## 6. Валидация и обработка ошибок

- Размер `spec` ≤ **1 МБ** → иначе `413`.
- Расширение/тип: `.yaml`/`.yml`/`text/yaml` → иначе `400`.
- `provider` по regex выше → иначе `400`.
- Любое исключение из ядра оборачивается в `422` с человекочитаемым `message` (ядро уже даёт понятные тексты через `GenerationError`).
- **Не роняй процесс на плохом вводе** — это отдельный оцениваемый пункт («понятные сообщения о результате и ошибках»). Всегда JSON с полем `error.code` и `error.message`.
- Логируй в stdout: `id`, provider, число предупреждений, итог (ok/failed).

## 8. Нефункциональные требования

- Синхронная генерация (без очередей) — на хакатоне достаточно; ответ за < 2 сек.
- CORS: если фронт отдаётся не тем же origin — разреши `GET/POST` для локалки.
- Таймаут генерации 10 сек, при превышении → `504` с понятным сообщением.
- Сервис стартует одной командой (см. DoD) — это критерий «понятный способ запуска».

## 10. Порядок работ

1. Согласовать фасад `Paybridge.generate` (раздел 2) и сделать заглушку.
2. `POST /api/integrations` + `store` + сериализация → на заглушке.
3. Скачивание файла и zip.
4. Валидация и ошибки (400/413/422/404/504).
5. Подключить реальное ядро вместо заглушки, прогнать на `examples/provider_api.yaml`.
6. Тесты, README, (опц.) страница `public/index.html`.

## 12. Расширенный бэклог (основная работа напарника)

Разделы 1–11 — это MVP (upload → generate → download). Его мало. Ниже — полный
бэклог. Порядок = приоритет. `S/M/L` — оценка объёма. В скобках — какой критерий
кейса усиливает.

### Блок A. Разбор и превью — показать силу парсера

- **A1 · `POST /api/validate` (dry-run)** `M` *(разбор спецификации, обработка ошибок)*
  Парсит спеку и возвращает распознанную модель **без генерации**: методы, auth,
  `status_map`, `error_map`, webhook, список предупреждений. UI показывает «что
  понято» до нажатия «Сгенерировать».
  Ответ: `{ endpoints[], auth, status_map, error_map, webhook, warnings[] }`.
- **A2 · `GET /api/integrations/:id/model`** `S` *(разбор)*
  Сохранённая модель распознавания для готовой интеграции (для превью в UI).

### Блок B. Качество сгенерированного кода — flagship

- **B1 · Синтакс-проверка результата** `M` *(качество реализации, обработка ошибок)*
  После генерации бэкенд вызывает `ruby -c` на `*_service.rb`. В ответ добавляется
  `"valid": true/false` и текст ошибки, если не скомпилировался. Ошибка компиляции —
  это `warning`, а не 500. Демонстрирует, что генератор даёт рабочий код.
- **B2 · `POST /api/integrations/:id/verify` — прогон fixtures** `L` *(доп. идея, полнота)*
  **Главная фича бэкенда.** Загружает `base_service.rb` + сгенерированный сервис,
  подменяет HTTP-клиент **мок-клиентом**, который по `fixtures.json` отдаёт заданные
  ответы, вызывает `create_request` / `fetch_status` / `process_callback` и сверяет
  результат с `expected_*`. Возвращает отчёт:
  ```json
  { "passed": 7, "failed": 0, "cases": [
    { "name": "create_request.response_201", "ok": true },
    { "name": "callback.failed", "ok": true, "expected": "rejected", "got": "rejected" }
  ] }
  ```
  Так на защите видно, что сгенерированная интеграция **реально работает**, а не
  просто «компилируется».

### Блок C. Мок-провайдер (advanced, если останется время)

- **C1 · Встроенный мок NovaPay из спеки** `L` *(доп. идея)*
  Поднимает эндпоинты провайдера (`POST /payouts`, `GET /payouts/{id}` …) и отвечает
  примерами из OpenAPI. Позволяет дёрнуть сгенерированный сервис **по сети**, а не
  только через мок-клиент.
- **C2 · Генерация webhook с корректной подписью** `M` *(доп. идея)*
  Мок шлёт `POST /webhooks/payout` с валидным `X-NovaPay-Signature` (HMAC), чтобы
  проверить `verify_signature!` и `process_callback` целиком.

### Блок D. Хранение и управление

- **D1 · SQLite-персистентность** `M` *(качество)*
  Заменить in-memory на `sqlite3` + репозиторий. Интеграции переживают рестарт.
  Интерфейс `Store` не меняется — только реализация.
- **D2 · `GET /api/integrations` (список + пагинация)** `S`
- **D3 · `DELETE /api/integrations/:id`** `S`
- **D4 · `POST /api/integrations/:id/regenerate`** `M` *(универсальность)*
  Хранить исходную спеку; регенерировать без повторной загрузки (напр. после правки
  `mapping.yml`).

### Блок E. Конфигурация и безопасность

- **E1 · Переопределение правил маппинга на лету** `M` *(расширение правил генерации)*
  Отдельный `mapping.yml` на интеграцию: через API/UI поменять статус/код-маппинг и
  перегенерировать. Прямо бьёт в критерий «предусмотрено добавление новых правил».
- **E2 · Хранение credentials на интеграцию** `M`
  `base_url`, `api_key`, `callback_secret` — задаются через API, наружу **не
  отдаются** (маскируются). Демонстрирует конфигурацию подключения.
- **E3 · API-ключ бэкенда + rate-limit + request-id в логах** `M` *(качество)*

### Блок F. Демонстрация и упаковка

- **F1 · Архив в структуре Rails-репозитория** `S` *(удобство)*
  Zip с раскладкой `app/services/provider/<name>_service.rb`, `spec/fixtures/…`,
  `README` — чтобы файлы сразу ложились в реальный проект.
- **F2 · UI: список интеграций + просмотр файлов с подсветкой + вкладка «что распознано»** `M` *(понятность демонстрации)*
- **F3 · CI (GitHub Actions) + Dockerfile** `M` *(качество, запуск одной командой)*
  Actions: `bundle install` + все тесты. `docker compose up` поднимает бэкенд.
- **F4 · Swagger/OpenAPI собственного API** `S`

## 13. Рекомендованный план по спринтам

1. **Спринт 1 (MVP+):** A1, B1, D2/D3 — превью распознавания, синтакс-чек, список.
2. **Спринт 2 (flagship):** **B2** (прогон fixtures) + F2 (UI отчёта). Это ядро демо.
3. **Спринт 3 (глубина):** D1 (SQLite), D4/E1 (регенерация + правила на лету).
4. **Спринт 4 (эффект):** C1/C2 (мок-провайдер), F1/F3 (упаковка, CI).

Минимум для сильной защиты: **A1 + B1 + B2 + F2**. Остальное — добор баллов за
универсальность, доп. идеи и качество.
