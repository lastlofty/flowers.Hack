# ТЗ напарнику: проверка, качество, документация, демо

**Кому:** второму разработчику команды.
**Обновлено по итогам QA-сессии.** Основной интерфейс — **CLI**. Веб — отдельный слой,
его делает **третий участник** (`ТЗ_веб.md`, скелет в `app/`), не твоя зона.

## Решения и канон из сессии (обязательно учесть)

- **CLI — основной интерфейс.** Веб — только если останется время.
- **Вход — всегда OpenAPI/Swagger** (структура), не свободный текст.
- **Репозиторий должен быть публичным.** Дедлайн коммита — **23:00**.
- **Присутствие на 3-м чекпоинте обязательно** минимум для одного участника.
- **`request_method`** в `create_request(operation, request_method)` — это **логический
  тип действия** (payment_method шлюза / `status` / `check`), НЕ HTTP-метод.
- **BaseService/harness настоящий не дадут** — контракт моделируем сами (`base_service.rb`).
- **Неоднозначное из `description` не угадываем молча:** структура → авто; неоднозначное →
  `warning` + опциональный **overrides-файл как механизм** (`amount_unit`, `required_if`,
  `signature_encoding`). Это НЕ минус за универсальность, пока overrides — механизм, а не
  хардкод в ядре.
- **Канон для NovaPay** (из задания): сумма в **копейках**; `bank_code` обязателен при
  `type=sbp`; подпись = **HMAC-SHA256(raw body, secret) → hex**; статусы
  `pending/processing → in_progress`, `completed → approved`, `failed/cancelled → rejected`.
  Все допущения — фиксируем в `INTEGRATION.md` / `DECISIONS.md`.

## Разделение ролей

| Ядро-генератор (владелец — тимлид) | Твоя зона |
|-----------------------------------|-----------|
| Парсер OpenAPI → модель | **Проверка сгенерированного сервиса** (прогон fixtures) |
| Генерация сервиса/доков/фикстур | **Корректность service-методов** (task 1 с доски) |
| Overrides-механизм и маппинг | CLI-UX и обработка ошибок |
| — | Корпус спецификаций для универсальности |
| — | Документация проекта (README, patterns & decisions) |
| — | Материалы демонстрации / речь |

## Задачи (привязаны к чекпоинтам)

### К 1-му чекпоинту — service-методы + базовая проверка

- **T1 · Корректность 4 методов контракта** `M` *(task с доски: create_request,
  fetch_status, process_callback, check_conditions)*
  Свериться, что сгенерированный сервис реализует контракт точно: сигнатуры, `success/
  failure`, обработка `RateLimitError`/`UnauthorizedError`, проверка подписи. По канону
  выше. Расхождения — багрепорт тимлиду.

- **T2 · Verification runner `integrate verify` (flagship)** `L` *(доп. идея, полнота)*
  CLI-команда: грузит `base_service.rb` + сгенерированный сервис, подменяет HTTP-клиент
  **мок-клиентом**, который по `fixtures.json` отдаёт заданные ответы, вызывает методы и
  сверяет с `expected_*`. Печатает отчёт:
  ```
  $ integrate verify --dir output/
  create_request.response_201   OK  (in_progress)
  callback.failed               OK  (rejected)
  fetch_status.response_200     OK  (approved)
  7 passed, 0 failed
  ```
  Это доказывает, что интеграция **реально работает**, а не просто компилируется. Ядро
  уже даёт `base_service.rb` и `fixtures.json` — нужен мок-клиент + сравнение + вывод.

### Ко 2-му чекпоинту — качество, тесты, документация

- **T3 · Генерация исполняемых тестов** `M` *(документация и тестовые материалы)*
  Кроме `fixtures.json` — генерировать `spec/<provider>_service_spec.rb` (minitest/RSpec)
  из фикстур, чтобы тесты запускались, а не только лежали данными.

- **T4 · CLI-UX и обработка ошибок** `M` *(удобство использования)*
  `--help`, понятный пошаговый вывод, коды возврата (0/1), внятные сообщения на битый
  YAML и на не-OpenAPI вход, режим `validate`/`--dry-run` (разбор без генерации через
  уже готовый `Paybridge.parse_only`).

- **T5 · Корпус для универсальности** `M` *(универсальность — 15 б.)*
  2–3 доп. спецификации разной формы (другой протокол/поля/авторизация) + batch-прогон:
  генерируем для каждой, проверяем `ruby -c` и `verify`. Один пример (`bluepay`) уже есть.

- **T6 · Документация проекта** `M` *(task с доски: patterns & decisions)*
  `README` (установка, запуск, примеры) + `DECISIONS.md`: канон, допущения, почему
  overrides-механизм, как расширять `mapping.yml`. Явно перечислить, что взято из
  структуры, а что — из `description`/канона.

### К 3-му чекпоинту — демо

- **T7 · Сценарий демонстрации + короткая речь** `S` *(task с доски + отраслевые баллы)*
  Живой прогон: `integrate --spec … → verify → показать сгенерированный сервис`. На двух
  провайдерах (доказать универсальность). 2–3 минуты, по делу.

### Не твоя зона

- **Веб** делает **третий участник** (см. `ТЗ_веб.md`, скелет в `app/`). Ты с ним
  стыкуешься только через тот же фасад (`Paybridge.generate` / `parse_only` / `verify`).

## Definition of Done

- [ ] `integrate verify --dir output/` проходит на novapay и на втором провайдере.
- [ ] Генерируются исполняемые тесты, `rake test` включает их.
- [ ] Битый YAML и не-OpenAPI вход → понятная ошибка, без стектрейса, код возврата 1.
- [ ] `README` + `DECISIONS.md` покрывают запуск, канон и допущения.
- [ ] Демо-сценарий отрепетирован, укладывается в регламент.
- [ ] Репозиторий **публичный**, ссылка отправлена **до 23:00**.

## План по чекпоинтам

1. **Чекпоинт 1:** T1 (методы верны) + T2 MVP (verify гоняет create/status/callback).
2. **Чекпоинт 2:** T3, T4, T5, T6 — тесты, UX, корпус, документация.
3. **Чекпоинт 3:** T7 — демо и речь. Публикация репо и сдача до 23:00.
