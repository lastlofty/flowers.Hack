# Безопасный запуск verify

HTTP `verify` не загружает сгенерированный Ruby в процесс Sinatra. Каждый запуск
происходит в новом контейнере из локального образа `ruby:3.2-bookworm`.
Небезопасного subprocess-fallback нет: без Docker/образа API возвращает
`503 verification_unavailable`, а генерация и скачивание продолжают работать.

## Подготовка среды

```bash
docker pull ruby:3.2-bookworm
docker image inspect ruby:3.2-bookworm
bundle exec rackup
```

Другой заранее проверенный образ можно указать через
`PAYBRIDGE_VERIFY_IMAGE`. Образ не скачивается автоматически при HTTP-запросе.
Timeout задаётся `PAYBRIDGE_VERIFY_TIMEOUT` (по умолчанию 10 секунд).

## Реальные ограничения запуска

- `--network none`;
- root filesystem контейнера read-only;
- каталог конкретной интеграции и два доверенных runner-файла подключаются
  отдельными read-only bind mount;
- storage целиком, исходная спецификация и окружение Sinatra не монтируются;
- процесс работает как uid/gid `65534`, capabilities удалены,
  `no-new-privileges` включён;
- лимиты: 128 МБ RAM, 0.5 CPU, 64 PID, 16 МБ временного `/tmp`;
- stdout — JSON-протокол до 1 МБ, diagnostics — до 64 КБ;
- при timeout runner завершает группу процессов и принудительно удаляет контейнер.

Это ограничение локального выполнения, а не гарантия безопасности самого Docker
daemon. Доступ к Docker socket должен иметь только доверенный процесс приложения.

## Проверенная приёмка

На искусственных данных проверены: отсутствие доступа к контрольному файлу за
пределами mount, невозможность TCP-соединения, завершение зависшего Ruby по timeout,
отсутствие оставшегося контейнера и два последовательных запуска одного provider с
разными версиями сервиса. Второй запуск использует свой файл и не видит класс первого.
